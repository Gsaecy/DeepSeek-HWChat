# 跨网络协作与产品化路线（PLAITCODE 合作总线）

> 这份文档是为了「怕忘记」和「一次把接口定死，避免以后重写」。
> 结论先行：**跨网络能做，而且局域网版 90% 可以复用**；能不能做大，取决于
> 我们把「消息中转」还是「协作语义 + 供应商中立」当作产品。

---

## 1. 目标与非目标

**目标**

1. 手机在任意网络下，能指挥家里/公司的多台电脑干活；
2. 一台电脑发起需求，多台设备、多个 agent 在同一个群里协作；
3. 同一个人可以把「公司的活」和「私活」分成互不串线的通道；
4. 别的编程工具（Cursor / Claude Code / Cline / Copilot / JetBrains）也能加入同一条协作线。

**非目标（至少现在不做）**

- 不做云端 IDE、不做代跑模型（算力和密钥仍在用户设备上）；
- 不做通用的「远程桌面」；
- 不承诺「一次发布就支持所有工具」——先打通协议，再逐个接。

---

## 2. 一句话架构

```
        手机 PWA            VS Code 扩展        别的 IDE / agent
           │                    │                     │
           │                 MCP server  ◄────────────┘
           └────────┬───────────┴──────────┐
                    ▼                      ▼
              传输层（可换）          身份层（可换）
        ┌───────────┼───────────┐   设备令牌 → GitHub OAuth
     局域网直连   中转服务器   隧道
                    │
              协作语义层（不变）
   需求 / 解析 / 追问 / 甲方回复 / 确认 / 进度 / 结果
   对齐账本：需求 × 平台 × 状态
```

**关键取舍：只有「传输」和「身份」会变，协作语义不变。**
局域网版已经把语义层写完了（`src/sync/lanProtocol.ts`），所以跨网络不是重写，是换插头。

---

## 3. 局域网版哪些能直接复用

| 现有件 | 跨网络时怎么用 |
|---|---|
| 群消息 / 需求 / 报告 / 对齐账本（`lanProtocol.ts`） | **原样复用**，连字段都不改 |
| 六阶段 + `groupAgreement` 状态机 | **原样复用**，追问未答不许执行 |
| 手机页面（`/m`） | 改成 PWA，接口从相对路径换到中转地址即可 |
| `POST /m/send` → `sendGroupMessage()` | **原样复用**，手机和群窗口仍是同一条管线 |
| 授权竞速（电脑 / 手机谁先点） | 复用，只是「谁在线」从局域网变成中转在线表 |
| 配对码 / 6 位码 | 升级为**设备令牌**（可撤销、可限权、可过期） |

要新写的只有三件：**中转服务**、**设备令牌与在线表**、**传输接口的第二个实现**。

---

## 4. 分三次交付，但接口一次定死

### 阶段 A：传输抽象 + 设备令牌（不改任何用户可见行为）

- 抽出 `Transport` 接口：`post(message)` / `poll(sinceId)` / `presence()`；
- 局域网实现 = 现有代码搬迁；
- 设备令牌：桌面生成、可撤销、绑定项目、可设权限（只读 / 可发言 / 可授权）；
- 验收：现有 1,429 条单测不回归，局域网行为一字不变。

### 阶段 B：中转服务（跨网络可用）

- 单个 Node 服务：WebSocket 长连接 + SQLite/Postgres + 短轮询兜底；
- 手机连中转、桌面连中转，中转**只转发不改语义**；
- 设备配对：桌面生成二维码 → 手机扫码 → 设备入列；
- 断线重连、离线补发（按消息 id 补）、在线表；
- 验收：两个不同网络（手机热点 + 家宽）真机跑通「手机发需求 → 两台电脑执行 → 结果回手机」。

### 阶段 C：账号与多通道（服务程序员的形态）

- GitHub OAuth 登录网站（身份），设备令牌仍由设备自己签；
- 通道（channel）= 一条协作线：一个项目 + 参与的设备 + 参与的 agent；
- 「公司活 / 私活」用**通道隔离**，跨通道绝不串消息、不共享账本；
- 网站：设备列表、通道、历史、审计日志、权限。

### 阶段 D：MCP server（兼容别的编程扩展）

- 把「合作总线」暴露成 MCP server：`team_status` / `team_say` / `team_ask` / `team_report`；
- 任何支持 MCP 的客户端接上就能加入同一条通道；
- 这样"兼容别的扩展"不用做 N 个插件，只维护一个协议面。

---

## 5. 多设备 / 多场景怎么不串线

- **一个通道一份账本**：`公司 app` 与 `我的小工具` 是两个通道，设备可以同时加入多个，但消息按通道隔离；
- **一个设备一个令牌、一个通道一个作用域**：公司电脑的令牌只签发给公司通道，撤销即失效；
- **可授权 ≠ 全权**：手机令牌默认「可发言、可看」，批准命令要单独开启（局域网版已经这么做了）；
- **审计**：每条需求、每次授权、每个结果都有设备、时间、通道，可导出。

---

## 6. 安全底线（这一条决定产品能不能活）

1. **端到端加密**：中转只看到密文与路由信息。命令、文件内容、代码片段不进服务器明文。
   没有这条，任何公司都不会允许装。
2. **最小权限 + 可撤销**：令牌绑通道、绑权限、可一键失效。
3. **授权必须双通道可见**：手机能批的前提是电脑上那张卡同时存在（现已实现竞速）。
4. **一份滥用预案**：中转要能限流、封禁、留痕，否则会被拿去当免费算力/跳板。
5. **不碰用户密钥**：模型 API key 永远只在设备本地。

---

## 7. 能不能做大（诚实版）

**有真实需求，但壁垒不在"中转"。**

- 中转服务器本身谁都能写，值钱的是：
  1. **甲方/乙方的协作语义**（解析 → 追问 → 确认 → 执行 → 验证），这是现在市场上没人做对的；
  2. **跨平台对齐账本**（Windows/macOS 两个版本做到哪一步，一张表说清）；
  3. **供应商中立**（MCP 接入任何 agent），大厂只会做自家闭环，这是我们唯一的结构性优势。
- 风险：
  - 大厂补齐多 agent 协作（时间问题，不是会不会）；
  - 安全事件一次就足够毁掉信任；
  - 排队等 MCP 生态成熟需要耐心；
  - 国内访问 GitHub 不稳定（本项目自己就靠代理推送），账号体系不能只依赖它。
- 现实路径：**自托管免费（开源引流）→ 托管中转订阅（按设备/席位）→ 团队版（审计、SSO、策略）**。
  先让自己每天用，再谈对外。

---

## 8. 已定 / 待定

**已定**

- 复用现有协作语义层，不改协议字段；
- 传输与身份做成可替换的两层；
- 手机页面保留，升级为 PWA；
- 授权竞速、六阶段、对齐账本都是产品的一部分，不是临时实现。

**待定（需要拍板）**

| 决策 | 选项 | 影响 |
|---|---|---|
| 中转部署在哪 | 自己的 VPS / Cloudflare Tunnel 打到家里一台机器 / 先本地跑通 | 决定阶段 B 的交付形态 |
| 端到端加密何时做 | 一开始就做 / 先明文跑通再补 | 先明文 = 以后要迁移数据模型 |
| GitHub 登录时机 | 先设备令牌、后 OAuth / 一开始就 OAuth | OAuth 需要中转持有 client secret |
